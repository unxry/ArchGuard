# Редактируемая магистерская ВКР ArchGuard AI

Основной результат — `ArchGuard_AI_VKR_MASTER.docx`. Научная база закрыта в P026 и P036;
подготовка текста не запускает анализаторы, не приобретает новые LLM-ответы и не меняет truth.
Архитектурное исследование является основным, Security рассматривается отдельно.

`source/` содержит главы и десять приложений; `assets/` — научные схемы в SVG и встроенные
PNG; `internal/references.json` и `internal/source-ledger.csv` — проверенные источники.
Проверки фактов, источников, оформления, структуры и страниц находятся в отчетах `THESIS_*`
и `VKR_COMPLIANCE_REPORT.md`. Неизвестные административные реквизиты перечислены отдельно
в `ADMIN_FIELDS_TO_FILL.md`; их наличие не является выполненной процедурой допуска к защите.

## Сборка и проверка

Используются Python с python-docx, Pillow и pypdf, Node.js с sharp и пакетный
`render_docx.py` навыка documents. В среде подготовки их пути получены через
`load_workspace_dependencies`; пользовательский LibreOffice не используется.
Переменные ниже обозначают пути к этим пакетным компонентам, без записи локальных путей
в распространяемые исходники или Word.

```sh
"$VKR_PYTHON" scripts/vkr_assets.py --node "$VKR_NODE" --plantuml "$VKR_PLANTUML"
"$VKR_PYTHON" scripts/build_vkr_docx.py --render-with "$VKR_RENDERER"
"$VKR_PYTHON" scripts/audit_vkr_docx.py
"$VKR_PYTHON" scripts/audit_vkr_layout.py --pdftotext "$VKR_PDFTOTEXT"
```

Сборщик задает стили, геометрию, нативные Office Math, таблицы, закладки, SEQ/REF,
PAGE/NUMPAGES и содержание TOC. Он сохраняет буквальный код DSL, проверяет разрешимость
цитат и создает кэш содержания из фактически отрендеренных страниц. При изменении пагинации
цикл сборки и рендеринга повторяется, максимум четыре раза. Это кэш настоящих полей Word,
а не оцененные номера страниц. После открытия и правок в Word: **Ctrl+A → F9**.

По прямому указанию автора абзацный отступ основного текста, разделов и библиографии
составляет **1,5 см**, межстрочный интервал — **1,5**. Это сознательное отклонение
от 1,25 см в найденном СТУ, которое требует согласования при нормоконтроле.
Таблицы оформлены по предоставленному образцу: тонкая черная сетка, выделенная шапка,
поля ячеек, одинарный интервал внутри, подпись сверху. Текст ячеек — 12 pt,
в широких числовых таблицах — 11 pt. Хронология сведена в три читаемые колонки
с сохранением всех исходных сведений. Схемы имеют редактируемые исходники
`assets/plantuml/`; графики используют только замороженные агрегаты.

Для контроля нужен установленный Times New Roman. Путь измерения таблиц по умолчанию
соответствует macOS; для другой среды можно передать собственный manifest с параметром
`table_measurement_font`. Непубличный manifest следует хранить в игнорируемом `tmp/`.
Сборщик создает там fontconfig и подключает каталог шрифта к пакетному рендереру, чтобы
не принять подстановку шрифта за проверку Times New Roman. Файлы шрифтов не публикуются.

После рендеринга координаты текста и номера проверяются на **всех** страницах;
визуально проверяются титул, бланк, содержание, все рисунки и таблицы с продолжениями,
библиография, отмеченные страницы и обычные страницы для сравнения. Точный перечень
и SHA-256 просмотренных изображений фиксируются в `internal/layout-review-final.json`. Промежуточный
PDF, изображения страниц, кэши шрифтов и временные файлы игнорируются Git и служат QA.
Основной deliverable — редактируемый DOCX. Для побитового повторения нужны те же версии
библиотек, шрифтов, исходников и assets; перенос между редакторами может менять верстку.

Счетчики слов и символов рассчитываются по видимому тексту тела OOXML, включая таблицы,
содержание и библиографию; словами считаются последовательности Unicode-букв/цифр с
внутренними дефисами. Поэтому число может отличаться от счетчика конкретной версии Word.
Число страниц берется из реального PDF, число рисунков/таблиц — из именованных объектов,
а повторные части одной таблицы не считаются новыми таблицами. Реферат использует итоговые
страницы, рисунки, таблицы, приложения и источники.

DOCX является рабочим master. Упоминание DOC/RTF в найденном СТУ и точная программа ГИА
требуют отдельной административной приемки; формальная сдача и проверка заимствований
не объявляются выполненными из факта успешной сборки.

Реальные снимки UI добавляются только после реализации и проверки соответствующего
сценария. Для них потребуется новая подпись, ссылка из текста, повторная сборка и QA;
текущая версия не содержит макетов, выданных за действующий интерфейс.
